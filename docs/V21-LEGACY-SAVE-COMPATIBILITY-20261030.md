# v21 기존 진행·저장 호환성 검수

현재 코어와 저장소 SHA-256을 고정하고 검수했다. 아래 결과는 **CPU 및 모의 IndexedDB 검사**다. 새 탄막의 전체 여정 완주나 실제 브라우저·GPU·모바일 기기 검증으로 분류하지 않는다.

| 검사 | 통과 | 실패·생략 | 범위 |
|---|---:|---:|---|
| 기존 제3리비전 자연 입력 재생 | 6 | 0 | 12개 전투 구성, 원래 HP·입력·종료 상태 |
| 기존 제4리비전 자연 입력 재생 | 6 | 0 | 18개 전투 구성, 원래 HP·입력·종료 상태 |
| 기존 제5리비전 자연 입력 재생 | 6 | 0 | 35개 전투 구성·105페이즈와 정본 결말 |
| 새 저장 호환성·경합 회귀 | 8 | 0 | 버전 보존, 백업, 구버전 창, 연습 격리 |

18개 원래 입력 파일 총 **3,699,860틱**을 그대로 재생했다. 변경된 체크포인트 **2,286개** 각각에서 복원 전후 최대 180개의 실제 후속 입력을 비교했다. 원래 입력 해시, 녹화 출처, 기대 종료 상태·페이즈·점수·체력은 수정하지 않았다. 테스트에 무적·777·체력·피해·RNG·타이머 변경은 없다. 이 18개는 필드가 없는 **기존 전투 규칙** 검증이다.

새 게임의 `combatRevision:21`은 검증·복원을 거쳐 유지된다. 이전 1~5 리비전 저장은 필드가 없는 원래 규칙으로 이어진다. 같은 실행 ID의 체크포인트를 저장하면서 전투 리비전을 바꾸는 시도는 거절한다.

이미 열려 있던 v20 창은 알 수 없는 체크포인트 필드를 지운 뒤 설정 저장으로 새 기록을 덮어쓸 수 있었다. 이를 막기 위해 새 저장에 `combatContract:21` 표식을 보존한다. **실제 배포된 v20 저장 코드 원본을 VM에서 실행**해, 이전 기록을 먼저 연 구버전 클라이언트가 새 기록 이후 설정을 저장하려 할 때 추가 쓰기 0회로 거절하고 원문을 내보낼 수 있음을 확인했다. 새 코드는 동일 기록을 정상 복원한다. 이는 모의 IndexedDB 실험이며 실제 다중 브라우저 창 시험으로 표시하지 않는다.

원시 로그는 `docs/v21-qa/*-final.log`, 입력·검사·출처 및 파일별 해시는 대응 JSON에 있다.

- 코어: `52cd164b1e429c1caeb69585c493aa33e2a17fc5eab06a4fd5ea86ba09c6193a`
- 저장소: `ec1010c11aaf3f49240f3fa8f46d5b85f922b6373bd4a29a5bd89a7ef282e71c`

이 해시가 바뀌면 후보 검증 해시와 결과를 다시 확인해야 한다.
